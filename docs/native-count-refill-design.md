# Wuwa Tappo 页面原生计数补次数设计

- 状态：已实现，并在 Wuwa Tappo 1.0.4 完成分级真实验证
- 目标：验证比高速 F24 更稳定、对系统输入队列影响更小的一次性补次数方案
- 当前适用对象：Wuwa Tappo 1.0.4 / WebView2 157.0.4341.46

## 1. 背景

当前 F24 方案在短任务中很快：

```text
1000 次约 2–9 秒
```

但持续数万次后，应用会停止处理合成键盘输入。已观测到两次：

```text
基准 573357，最终 619988，发送 47500
基准 618056，最终 662277，发送 45000
```

两次请求最终均为 `needs_focus`。即使执行两次 UIA `InvokePattern`，字符数也没有继续变化。

现象说明：

- Worker、控制面板和 Wuwa Tappo 进程都没有崩溃；
- 不是内存耗尽；
- 不是网络断开；
- 应用本身仍能显示宝箱和响应界面；
- 停止的是应用对持续合成键盘输入的计数处理。

当前 F24 批次会在一次 `SendInput` 中快速放入大量 keydown/keyup，速率约 300–450 次/秒，远高于同类成熟项目的常见速率。

## 2. GitHub 方案调查

### 2.1 AutoTappo

仓库：

```text
https://github.com/To0Ru/AutoTappo
```

主要做法：

- 使用 F21–F24 幻影键；
- 每次只发送一个键；
- 按住时间约 10–32 ms；
- 频率约 8–50 次/秒；
- 随机间隔和偶发停顿；
- 用户键盘或鼠标操作时主动暂停。

价值：

- 证明 F21–F24 都能被当前应用计数；
- 说明单次输入、较低频率的连续模式比超大突发更接近成熟实现。

### 2.2 WuwaTappo Companion Tools

仓库：

```text
https://github.com/Chuniex-0631/WuwaTappo-Companion-Tools
```

主要做法：

- F24 单次按下和抬起；
- 固定约 50 次/秒；
- 没有采用当前项目 500 键一次突发的模式。

### 2.3 WuwaTappo Helper

仓库：

```text
https://github.com/kano0222/WuwaTappo-helper
```

该项目的核心价值不是继续降速，而是改为页面原生计数：

```text
宿主命令行参数
  -> 只监听回环地址的 WebView2 CDP
  -> 页面能力发现
  -> 调用页面已有的增量函数
  -> 调用页面已有的强制保存函数
  -> 核对页面状态和保存结果
```

已验证的关键宿主参数：

```text
--edge-webview-switches="--remote-debugging-address=127.0.0.1 --remote-debugging-port=<port>"
```

此前仅设置环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，没有开放调试端口。正确做法是直接向 `WuwaTappo.exe` 传入上述宿主参数。

该项目当前使用或兼容的页面能力包括：

```text
incrementLocalClickCount()
addLocalClickCount()
save_key_press_count({ force: true })
applyClickReportSuccess()
```

限制：

- 该类函数属于页面内部实现，不是公开 API；
- 上游项目只明确完成过 1.0.3 的有限真实验证；
- 本项目已独立验证 1.0.4 的 1000、5000 和 50000 次补数；
- 项目本身也提示用户协议和账号风险。

## 3. 推荐架构

### 3.1 进程与连接

```text
管理员一次性启动器
  -> 选择随机回环端口
  -> 启动 WuwaTappo.exe 并传入 edge-webview-switches
  -> Worker 通过 127.0.0.1 CDP 连接
  -> 完成后请求桌宠正常退出
  -> 以无调试参数模式重新启动
```

安全要求：

- 只监听 `127.0.0.1`；
- 每次使用随机端口；
- 不读取 Cookie、Token、Authorization 或账号资料；
- 调试启动只用于当前一次性任务；
- Host 被强制结束时，提示用户手动重启桌宠。

### 3.2 页面能力发现

连接成功后不直接执行固定字符串，而是先验证：

1. 页面来自 `tauri.localhost`；
2. 当前窗口是桌宠主窗口；
3. 应用资源可读取；
4. 计数 store 唯一存在；
5. 增量函数和保存函数签名匹配；
6. 登录状态与账号不可逆摘要可读取；
7. 任一能力缺失时停止，不猜测接口。

### 3.3 单批补数

当前实现：

```text
单批上限：1000
```

每批流程：

```text
1. 读取 before 快照
2. 校验账号摘要、登录状态和本次四项基准值
3. 同一事件循环内执行 N 次 incrementLocalClickCount
4. 每轮校验 local/cumulative/available 增量
5. 调用 save_key_press_count({ force: true })
6. 等待保存完成，设置超时
7. 读取 after 快照
8. 校验保存后的登录状态、可用次数和累计次数
9. 确认成功后才进入下一批
```

禁止：

- 多批并发；
- 保存未完成时继续增加；
- 超时后自动重发同一批；
- 旧服务器计数覆盖本地计数后继续盲加。

### 3.4 不确认状态

出现以下任一情况时停止并保留 pending：

```text
CDP 断开
页面重新加载
函数签名变化
登录账号变化
保存失败或超时
保存后的可用次数或累计次数未达到本批目标
登录账号或页面 store 发生变化
```

pending 记录必须包含：

```text
operation_id
request_id
账号的不可逆摘要
before 快照
请求增量
已确认增量
保存阶段
最后错误
时间
```

不得自动重放结果未知的增量操作。

## 4. 性能实测

可能优于 F24 的原因：

- 不向 Windows 全局输入队列写入数万个键盘事件；
- 不需要 UIA 高频扫描字符数；
- 页面内 JS 循环 1000–2000 次开销很小；
- 一个 CDP 连接即可完成多批操作。

实际吞吐主要由 `save_key_press_count` 和服务器状态同步决定，而不是 JS 循环本身。

2026-11-14 实测：

| 增量 | 起始可用次数 | 最终可用次数 | 结果 |
|---:|---:|---:|---|
| 1000 | 550407 | 551407 | 通过 |
| 5000 | 551407 | 556407 | 通过 |
| 50000 | 551407 | 606407 | 通过 |

50000 次的页面增加阶段约 26.1 秒，相当于约 1915 次/秒；Host 工作集约 45.7 MB，未观察到随批次线性增长。每次 Host 都正常退出，Wuwa Tappo 以无调试参数模式重新启动。

### 4.1 长任务恢复版

针对页面约 30 秒一次的本地状态归并，恢复版不再把 `localClickCount` 和 `serverClickConsume` 与上一批完全相等作为阻断条件。批次状态机按以下边界处理：

```text
写入前 store-state-changed
  -> 重新读取页面快照
  -> 账号不变且 available/cumulative 未倒退
  -> 按最新状态重算剩余量，最多连续 5 次

写入中 increment-not-confirmed
  -> 已安全保存的部分增量按最新快照计入
  -> 只补差额，不重发整批，最多连续 5 次

保存后 post-save-state-not-confirmed
  -> 只读轮询，不执行增量函数
  -> 核心计数前进则确认
  -> 5 次均未前进且 local 归零时，按实际绝对计数安全重基准
  -> 核心计数部分变化时停止，避免重复增加

CDP/WebSocket 断开
  -> 正常恢复 Wuwa Tappo
  -> 新会话重新读取绝对计数和账号摘要
  -> 按原始绝对目标计算 remaining
  -> 最多恢复 3 次
```

成功完成条件同时要求 `available` 和 `cumulative` 达到任务开始时各自加上的目标增量。结构化日志记录冲突现场、剩余量、重试次数和总耗时，不记录账号原值或凭据。

最终恢复版实测：

| 请求增量 | 起始 available | 最终 available | 耗时 | 安全回滚重基准 | 结果 |
|---:|---:|---:|---:|---:|---|
| 500,000 | 2,355,575 | 2,855,575 | 262.8 秒 | 1 | 通过 |
| 1,000,000 | 2,855,575 | 3,855,575 | 525.1 秒 | 2 | 通过 |

两轮累计计数均同步精确增加相同数量，Host 结束后恢复普通模式，没有遗留调试端口。

## 5. 测试阶梯与完成情况

禁止直接测试 200000。顺序如下：

```text
1. 只读发现：不增加计数
2. 单次增加：+1
3. 单批：+1000
4. 重复批：+5000
5. 长任务：+50000
6. 最终验证：+500000
7. 上限验证：+1000000
```

已完成 1–7 级。500,000 和 1,000,000 次均为最终恢复版真实验证。单次通过不能证明统计意义上的 99%，但已验证原先至少两类中断可在不重复计数的情况下恢复。

每级必须记录：

- 起始和最终字符数；
- 保存前后的 cumulative/local/available；
- 每批耗时；
- Worker 工作集；
- 进程 CPU 时间；
- 是否出现服务器回执覆盖；
- 是否存在 pending；
- 调试端口是否仅监听回环地址；
- 任务结束后是否恢复普通启动。

已确认：

- 1000、5000、50000 次的可用与累计次数均精确增加；
- 调试端口只监听 `127.0.0.1`；
- Host 在正常路径退出，Wuwa Tappo 进程由普通参数重新创建；
- 任务结束后没有遗留监听端口或 Host 进程。

## 6. 与当前 F21–F24 模式的关系

页面原生计数 Host 是独立一次性入口；主 Worker 仍保留 F21–F24 输入模式：

```text
single：仅使用配置的 virtualKey
chord：同时按下 F21+F22+F23+F24
cycle：依次循环 F21–F24
```

`chord` 已在 1.0.3 上做过单次验证：

```text
同时按放 F21+F22+F23+F24
字符数增加 4
```

但它仍然经过应用输入处理，无法从根本上消除长时间后的输入门控。

## 7. 待确认事项

- 当前 1.0.4 的 2000 次单批页面内循环是否稳定；
- `save_key_press_count` 的真实耗时和失败率；
- 服务器回执是否会覆盖大批量本地计数；
- 200000 次长任务是否需要主动分批冷却；
- 任务结束后普通的进程退出/重启是否总能关闭调试端口；
- 后续应用更新导致的函数签名变化。

## 8. 为什么不直接调用服务器 HTTP 补次数

可以只读调查页面网络请求，但不把伪造或重放服务器补数写请求作为交付功能：

- 当前页面 store 同时存在 `serverClickTotal`、`serverClickConsume` 等服务端状态，不能把应用认定为完全离线的单机程序；
- 直接写服务器接口需要处理登录身份、签名、风控和幂等语义，任一判断错误都可能造成账号状态异常；
- “不会封号”无法由本地测试证明，用户对账号风险的乐观判断不能替代服务端规则；
- 页面原生路径可把操作限制在当前已登录页面，并在每批后复核，验证成本更低。

因此，HTTP 只用于只读调查；实际批量补数使用页面原生方案。
