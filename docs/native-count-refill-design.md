# Wuwa Tappo 页面原生计数补次数设计

- 状态：设计保留，尚未实现
- 目标：验证比高速 F24 更稳定、对系统输入队列影响更小的一次性补次数方案
- 适用对象：Wuwa Tappo 1.0.3 / Tauri + WebView2

## 1. 背景

当前 F24 方案在短任务中很快：

```text
1000 次约 2–9 秒
```

但持续数万次后，应用会停止处理合成键盘输入。已观测到两次：

```text
基准 573357，最终 619988，发送 47500
基准 618056，最终 662277，发送 45000
```

两次请求最终均为 `needs_focus`。即使执行两次 UIA `InvokePattern`，字符数也没有继续变化。

现象说明：

- Worker、控制面板和 Wuwa Tappo 进程都没有崩溃；
- 不是内存耗尽；
- 不是网络断开；
- 应用本身仍能显示宝箱和响应界面；
- 停止的是应用对持续合成键盘输入的计数处理。

当前 F24 批次会在一次 `SendInput` 中快速放入大量 keydown/keyup，速率约 300–450 次/秒，远高于同类成熟项目的常见速率。

## 2. GitHub 方案调查

### 2.1 AutoTappo

仓库：

```text
https://github.com/To0Ru/AutoTappo
```

主要做法：

- 使用 F21–F24 幻影键；
- 每次只发送一个键；
- 按住时间约 10–32 ms；
- 频率约 8–50 次/秒；
- 随机间隔和偶发停顿；
- 用户键盘或鼠标操作时主动暂停。

价值：

- 证明 F21–F24 都能被当前应用计数；
- 说明单次输入、较低频率的连续模式比超大突发更接近成熟实现。

### 2.2 WuwaTappo Companion Tools

仓库：

```text
https://github.com/Chuniex-0631/WuwaTappo-Companion-Tools
```

主要做法：

- F24 单次按下和抬起；
- 固定约 50 次/秒；
- 没有采用当前项目 500 键一次突发的模式。

### 2.3 WuwaTappo Helper

仓库：

```text
https://github.com/kano0222/WuwaTappo-helper
```

该项目的核心价值不是继续降速，而是改为页面原生计数：

```text
宿主命令行参数
  -> 只监听回环地址的 WebView2 CDP
  -> 页面能力发现
  -> 调用页面已有的增量函数
  -> 调用页面已有的强制保存函数
  -> 核对页面状态和保存结果
```

已验证的关键宿主参数：

```text
--edge-webview-switches="--remote-debugging-address=127.0.0.1 --remote-debugging-port=<port>"
```

此前仅设置环境变量 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，没有开放调试端口。正确做法是直接向 `WuwaTappo.exe` 传入上述宿主参数。

该项目当前使用或兼容的页面能力包括：

```text
incrementLocalClickCount()
addLocalClickCount()
save_key_press_count({ force: true })
applyClickReportSuccess()
```

限制：

- 该类函数属于页面内部实现，不是公开 API；
- 当前项目只明确完成过 1.0.3 的单次增加和保存真实验证；
- 大批量计数竞争、服务器回执、长任务稳定性仍需本项目自行验证；
- 项目本身也提示用户协议和账号风险。

## 3. 推荐架构

### 3.1 进程与连接

```text
管理员一次性启动器
  -> 选择随机回环端口
  -> 启动 WuwaTappo.exe 并传入 edge-webview-switches
  -> Worker 通过 127.0.0.1 CDP 连接
  -> 完成后请求桌宠正常退出
  -> 以无调试参数模式重新启动
```

安全要求：

- 只监听 `127.0.0.1`；
- 每次使用随机端口；
- 不读取 Cookie、Token、Authorization 或账号资料；
- 调试启动只用于当前一次性任务；
- Host 被强制结束时，提示用户手动重启桌宠。

### 3.2 页面能力发现

连接成功后不直接执行固定字符串，而是先验证：

1. 页面来自 `tauri.localhost`；
2. 当前窗口是桌宠主窗口；
3. 应用资源可读取；
4. 计数 store 唯一存在；
5. 增量函数和保存函数签名匹配；
6. 登录、更新锁和领取状态可读取；
7. 任一能力缺失时停止，不猜测接口。

### 3.3 单批补数

首版建议：

```text
单批上限：1000
验证通过后：2000
```

每批流程：

```text
1. 读取 before 快照
2. 校验账号、登录状态、更新锁、宝箱状态
3. 同一事件循环内执行 N 次 incrementLocalClickCount
4. 每轮校验 local/cumulative/available 增量
5. 调用 save_key_press_count({ force: true })
6. 等待保存完成，设置超时
7. 读取 after 快照
8. 校验保存结果和服务器回执
9. 确认成功后才进入下一批
```

禁止：

- 多批并发；
- 保存未完成时继续增加；
- 超时后自动重发同一批；
- 旧服务器计数覆盖本地计数后继续盲加。

### 3.4 不确认状态

出现以下任一情况时停止并保留 pending：

```text
CDP 断开
页面重新加载
函数签名变化
登录账号变化
更新锁出现
宝箱状态变化
保存失败或超时
服务器回执被旧状态覆盖
本地与服务器计数无法对应
```

pending 记录必须包含：

```text
operation_id
request_id
账号的不可逆摘要
before 快照
请求增量
已确认增量
保存阶段
最后错误
时间
```

不得自动重放结果未知的增量操作。

## 4. 性能预期

可能优于 F24 的原因：

- 不向 Windows 全局输入队列写入数万个键盘事件；
- 不需要 UIA 高频扫描字符数；
- 页面内 JS 循环 1000–2000 次开销很小；
- 一个 CDP 连接即可完成多批操作。

实际吞吐主要由 `save_key_press_count` 和服务器状态同步决定，而不是 JS 循环本身。

因此不能提前承诺固定速度，应以实测为准。

## 5. 测试阶梯

禁止直接测试 200000。顺序如下：

```text
1. 只读发现：不增加计数
2. 单次增加：+1
3. 单批：+1000
4. 重复批：+5000
5. 长任务：+50000
6. 最终验证：+200000
```

每级必须记录：

- 起始和最终字符数；
- 保存前后的 cumulative/local/available；
- 每批耗时；
- Worker 工作集；
- 进程 CPU 时间；
- 是否出现服务器回执覆盖；
- 是否存在 pending；
- 调试端口是否仅监听回环地址；
- 任务结束后是否恢复普通启动。

## 6. 与当前 F21–F24 模式的关系

页面原生计数方案实现前，继续保留 F21–F24 输入模式：

```text
single：仅使用配置的 virtualKey
chord：同时按下 F21+F22+F23+F24
cycle：依次循环 F21–F24
```

`chord` 已在当前 1.0.3 上做过单次验证：

```text
同时按放 F21+F22+F23+F24
字符数增加 4
```

但它仍然经过应用输入处理，无法从根本上消除长时间后的输入门控。

## 7. 待确认事项

- 当前 1.0.3 的 2000 次页面内循环是否稳定；
- `save_key_press_count` 的真实耗时和失败率；
- 服务器回执是否会覆盖大批量本地计数；
- 200000 次长任务是否需要主动分批冷却；
- 任务结束后普通的进程退出/重启是否总能关闭调试端口；
- 后续应用更新导致的函数签名变化。
